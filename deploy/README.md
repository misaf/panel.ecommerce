# Vendra ecosystem — Traefik reverse-proxy stack

This directory is the source of truth for the reverse-proxy stack. On a server
each subfolder is deployed to `/opt/apps/<name>/` (they are independent Compose
projects; paths in the examples below use the `/opt/apps` layout). The
architecture doc explains every decision:
<https://claude.ai/code/artifact/9b061b4a-a494-40b1-a491-7a6e72317fee>

One Traefik v3 instance is the only public entrypoint. Every app is an
independent Docker-Compose project discovered over the shared `traefik-public`
network. Nothing but Traefik binds `80/443`.

```
/opt/apps/
  proxy/              Traefik v3 (owns 80/443)
  vendra/             Laravel backend overlay (admin/console/reseller/api → :8080)
  vendra-website/   apex marketing site (Next.js :3000)
  property-template/  template used to scaffold storefront properties
  properties.yml      the property REGISTRY (committed — the fleet's definition)
  properties/<slug>/     one per customer, generated by stack.sh (gitignored)
```

No customer's generated files or secrets are committed. What *is* committed is
`properties.yml`: slug, domain and image per property. Without it a rebuilt host
would have no record of what was running on it, and the disaster-recovery story
below ("git + restore volumes") would not hold. `bin/stack property sync`
re-renders every `properties/<slug>/` from it.

## Host map

| Host | Serves | Container |
|---|---|---|
| `vendra.test` | Marketing site | vendra-website :3000 |
| `admin.vendra.test` | Tenant admin — bare host resolves no tenant, 404s | vendra-php-panels :8080 |
| `<slug>.admin.vendra.test` | Tenant admin (canonical) | vendra-php-panels :8080 |
| `admin.<customer-domain>` | Tenant admin (custom domain) | vendra-php-panels :8080 |
| `console.vendra.test` | Platform console | vendra-php-panels :8080 |
| `reseller.vendra.test` | Reseller panel | vendra-php-panels :8080 |
| `api.vendra.test` | **Canonical API (only API)** | vendra-php-api :8080 |
| `<customer-domain>` | Storefront (frontend only) | its own :3000 |

Storefronts call **only** `https://api.<BASE_DOMAIN>`. Customer domains serve no
API. Because that one host serves every property, the tenant cannot come from
the host there: `ResolveApiTenant` falls back to the request `Origin` (then
`Referer`), matched against the active tenant domains — the same data behind the
CORS allowlist below, so a property registers its domain once. A storefront
rendering on the server has no browser-set `Origin` and must send its own public
origin. Requests to `api.<base>` with no recognised origin 404, and the fallback
applies to that host alone — every panel host shape still resolves by host only.

There is **one** admin panel, not two: `AdminPanelServiceProvider` sets no
`->domain()`, so it is tenant-scoped by whatever host resolves through
`DomainTenantFinder`. `admin.<base>`, `<slug>.admin.<base>` and
`admin.<customer-domain>` are three host shapes for that same panel, served by a
pair of routers that differ only in which ACME challenge their certificate uses.
The platform-level surface is `console`, a separate panel with its own auth guard.

The panels and the API run as **two containers from the same image**
(`php` and `php-api`), so a slow admin report cannot starve storefront API
traffic of PHP workers, and the API scales on its own. The five platform routers
live in `proxy/traefik/dynamic/vendra.yml`, not on container labels.

Because storefronts are served on customer domains but fetch from `api.<base>`,
every storefront API call is cross-origin. The allowed origins are the *active
tenant domains*, injected per request — see `app/Http/Middleware/
HandleStorefrontCors.php`. Onboarding a property therefore updates CORS
automatically; there is no list to maintain.

## First-time host setup

```bash
docker network create traefik-public

cd /opt/apps/proxy
cp .env.example .env                 # set BASE_DOMAIN; prod: CERT_RESOLVER_DNS=letsencrypt-dns
touch traefik/acme/acme.json && chmod 600 traefik/acme/acme.json   # prod only
# edit traefik/traefik.yml → ACME email; edit dynamic/middlewares.yml → dashboard hash
docker compose up -d
```

## Deploy vendra

```bash
cd /opt/apps/vendra
cp .env.example .env                 # BASE_DOMAIN + DB creds (cert resolvers live in proxy/.env)
docker compose \
  -f /opt/apps/vendra-src/docker/docker-compose.yml \
  -f docker-compose.traefik.yml \
  --env-file .env up -d
```

## Add a new property

A **property** is a tenant store that belongs to a **reseller**. It has two
halves:

1. **Backend property/tenant** — created in Vendra (owns the admin at
   `<slug>.admin.<base>` and its data), provisioned by the app and attached to a
   reseller:
   ```bash
   php artisan vendra-subscription:provision "Abbas" abbas.com abbas_owner owner@abbas.com \
     --reseller=<reseller-id-or-slug> --plan=<plan>
   ```
2. **Storefront frontend** — the public Next.js site for that property, scaffolded
   by `stack.sh` (no folder is committed):
   ```bash
   bin/stack property add abbas abbas.com ghcr.io/your-org/abbas-storefront@sha256:<digest>
   bin/stack property up  abbas
   # Point the property domain's DNS A/AAAA record at this host.
   ```

`property add <slug> <domain> [image]` writes `properties/<slug>/` from
`property-template/` (its own independent Compose project), records the property
in `properties.yml`, and in local dev regenerates the self-signed cert to cover
the new domain. **Commit `properties.yml`** — it is the fleet's only durable
record. Edit `properties/<slug>/.env` any time (`STOREFRONT_IMAGE`,
`STOREFRONT_PORT`, …). Other property commands: `property up|down|restart|rm
<slug>`, `property ls` and `property sync`.

Pin storefront images **by digest** (`…@sha256:…`) in production: with a moving
tag a restart can silently ship a different build.

### Property creation from the panels

Both `console.<base-domain>` and `reseller.<base-domain>` collect the complete
florist storefront configuration while creating a property. Console operators
may disable storefront creation; reseller owners cannot. The property tenant is
committed first and a `storefront_deployments` request is then persisted.

Configure the authenticated asynchronous provisioner in Vendra's environment:

```dotenv
STOREFRONT_PROVISIONER_URL=https://deploy.example.com/storefronts
STOREFRONT_PROVISIONER_TOKEN=replace-with-a-secret-token
STOREFRONT_THEMES=default
```

The provisioner receives the tenant ID, slug, domain, selected theme, and full
property configuration as JSON. It builds `vendra-storefront-florist`, publishes
the property-specific image, registers its immutable digest with the deployment
control plane, and returns `status`, `reference`, and `image_digest`. Vendra
records `pending`, `processing`, `requested`, `ready`, or `failed`; without a
configured URL the request intentionally remains `pending`, and no shell command
is executed from the web process.

## Running the full stack locally (no /opt copy)

You can run everything straight from this `deploy/` directory in the repo — the
compose files use relative paths. The realistic local outcome: **proxy + backend
up, with the admin, console, reseller panels and the API all reachable over
HTTPS.** Storefront and marketing containers stay down until you have Next.js
images to point them at (that is application work, not infrastructure).

### The quick way — `stack.sh`

`bin/stack` (a thin wrapper around `deploy/stack.sh`) drives the whole proxy +
backend lifecycle (creates the network, copies `.env` files on first run, starts
both projects, prints the URLs). Run it from the repo root; `./deploy/stack.sh`
works too.

| Command | What it does |
|---|---|
| `bin/stack up --build` | First run — builds the image, then network + proxy + backend |
| `bin/stack up` | Subsequent starts (no rebuild) |
| `bin/stack down` | Stop properties + backend + proxy |
| `bin/stack restart [--build]` | `down` then `up` |
| `bin/stack status` | Health-check the whole stack (docker, ports, cert, containers, endpoints) |
| `bin/stack logs [target]` | Follow logs — default vendra `php`; also `proxy`, a vendra service, or a property |
| `bin/stack open <target>` | Open a URL: `admin`\|`api`\|`console`\|`reseller`\|`dashboard`\|`<property>` |
| `bin/stack hosts [--write]` | Print (or append, with sudo) the `/etc/hosts` entries for every stack host |
| `bin/stack ps` | Docker status of proxy + vendra + properties |
| `bin/stack urls` | Reprint the local URLs |
| `bin/stack property sync` | Re-render `properties/` from the committed `properties.yml` |

Run `bin/stack help` (or no argument) for full usage. `bin/stack status` is the
quickest way to see what's wrong if a page won't load.

### One-time setup the script does *not* do

These are environment-specific, so you run them once by hand:

1. **Free ports `80/443`** — Traefik must own them; stop anything already bound
   (`sudo lsof -nP -iTCP:80 -sTCP:LISTEN` to check).
2. **Resolve `.test` → 127.0.0.1** — easiest via the helper (appends only what's
   missing, for base hosts + every property):
   ```bash
   bin/stack hosts --write     # or `bin/stack hosts` to print without writing
   ```
3. **Trusted certs (optional)** — without this Traefik serves a self-signed cert
   and the browser warns (still fine with `curl -k`). To trust it:
   ```bash
   brew install mkcert nss && mkcert -install
   mkcert -cert-file deploy/proxy/traefik/certs/local.pem \
          -key-file  deploy/proxy/traefik/certs/local-key.pem \
          "vendra.test" "*.vendra.test" "*.admin.vendra.test" \
          <your-property-domains…>
   ```
   Keep `CERT_RESOLVER_DNS` (proxy) and `CERT_RESOLVER` (properties) **empty** locally.
   (If you skip mkcert, `stack.sh` auto-generates a self-signed cert and extends
   it to cover each property domain as you add one.)
4. **Dashboard auth** — before opening `https://traefik.vendra.test`, set a real
   basic-auth hash in `proxy/traefik/dynamic/middlewares.yml`
   (`htpasswd -nbB admin '<pw>'`).

Then just `bin/stack up --build`.

### Verify

```bash
curl -k https://api.vendra.test/up         # → 200
curl -kI https://admin.vendra.test/         # → 302 /login
```

Then browse `https://admin.vendra.test`, `console.vendra.test`,
`reseller.vendra.test`, and the Traefik dashboard.

> Note: behind the Traefik overlay **nothing but Traefik publishes a port** —
> the overlay clears the base compose's `127.0.0.1:3306` MySQL and `:8025`
> Mailpit bindings. To reach MySQL from the host for debugging, use
> `docker compose … exec mysql mysql -u…`, or start the backend without the
> overlay.

### Storefront properties

Each customer storefront is scaffolded on demand (needs a built Next.js image):

```bash
bin/stack property add abbas abbas.test ghcr.io/your-org/abbas:latest
bin/stack hosts --write      # adds abbas.test (+ its admin subdomain) to /etc/hosts
bin/stack property up abbas
```

`property add` writes `properties/abbas/` (gitignored) and extends the local cert to
cover `abbas.test`. Manage with `property up|down|restart|rm <slug>` and `property ls`;
`stack.sh down` stops all properties too. The marketing site
(`vendra-website/`) is a fixed project you bring up the same way once you have
its image.

## Production certificates

Which challenge a host uses follows from **who controls its DNS**:

```
# proxy/.env — every PLATFORM host (apex, admin, <slug>.admin, console,
# reseller, api, dashboard). ONE wildcard cert covers all of them.
CERT_RESOLVER_DNS=letsencrypt-dns

# properties/<slug>/.env — storefronts only. Their DNS is the customer's, so
# DNS-01 is not available; HTTP-01 needs nothing but an A record.
CERT_RESOLVER=letsencrypt
```

The wildcard (`<base>` + `*.<base>` + `*.admin.<base>`) means one issuance path
instead of five, it keeps working when port 80 is filtered, and it is the only
challenge that can cover the per-tenant admin subdomains — which are created
without a redeploy. `letsencrypt-dns` needs a scoped DNS-provider token
(`CF_DNS_API_TOKEN` in `proxy/.env` for Cloudflare); scope it to the one zone.

## Zero-downtime deploys

Both backends declare a Traefik health check, so Traefik stops routing to a
container that is booting or shutting down. To restart without a 502 window,
scale up before recreating:

```bash
docker compose -p vendra --env-file deploy/vendra/.env \
  -f docker/docker-compose.yml -f deploy/vendra/docker-compose.traefik.yml \
  up -d --scale php-api=2 --no-recreate
```

Verify with a loop against `https://api.<base>/up` while it runs — you should see
no non-200 responses.

## Secrets, backup and recovery

The irreplaceable state on a host is small and worth naming:

| What | Why it matters |
|---|---|
| MySQL data | The only unrecoverable business state. Dump or snapshot offsite; **test restores**. |
| `proxy/traefik/acme/acme.json` | Losing it means re-issuing every cert — watch Let's Encrypt rate limits. `chmod 600`. |
| every `.env` | DB credentials, `APP_KEY`, the DNS token. |
| `properties.yml` | The fleet definition. Committed, so git is its backup. |

Redis is a cache — treat it as disposable. Storefront images live in a registry;
that *is* their backup.

Keep `.env` files **encrypted at rest** (SOPS/age, or your secrets manager) and
never commit a real value. Recovery on a fresh host is then: clone the repo,
restore volumes and the decrypted `.env` files, `bin/stack property sync`,
`bin/stack up`.

## Security notes

- Traefik does **not** mount the Docker socket. It talks to a read-only
  `docker-socket-proxy` sidecar on an `internal` network, because *read* access
  to the real socket exposes every container's environment — i.e. every secret
  in every `.env`.
- No datastore publishes a port; in production Traefik is the only container on
  the host that publishes anything.
- Every container caps its json-file logs (`max-size`/`max-file`). On a single
  host an unrotated log is the fastest way to fill the disk.
- Traefik's access log keeps `X-Request-ID`, which the app already generates and
  echoes (`App\Http\Middleware\AddRequestContext`), so an edge log line joins
  its application log line on one id. An OTLP tracing block is ready to
  uncomment in `traefik/traefik.yml`.
